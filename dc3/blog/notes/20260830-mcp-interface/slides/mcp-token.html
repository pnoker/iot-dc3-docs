IoT DC3 · 开源工业物联网手记 · EP.07

令牌统一：一套身份、一个签发方、权限不因协议而变大

智能体接口最大的风险面在认证——DC3 的解法是把三个入口收进同一套身份体系
令牌生命周期 · 一个签发方
1
签发 OAuth 2.0 · client_credentials
Web 端 / CLI / 智能体客户端共用同一套身份体系，不另造令牌通道
2
携带 JWT · RS256 非对称签名
资源侧用公钥验签，不需要回源查询——网关与 /mcp 端点统一校验
3
校验 验签 → scope → 租户上下文
任何一层不满足即终止；调用全程落入审计账本
落地状态：OAuth 网关开关已可在 compose 中启用 · 活栈验证通过（RS256 验签全通）
scope 从哪来 · RBAC 投影
平台 RBAC 角色
用户在管理台的真实权限——唯一权限真相源
投影（projection）· 不另造权限模型
MCP scope
智能体令牌的能力边界，由角色推导而来
call（基础调用） call_high（高危附加项） 只读集合
各 scope 非互斥：call_high 是 call 之上的附加授权
红线：智能体拿到的每一分能力，都是某个真实用户显式授权出去的——用户是什么角色，令牌就是什么能力
风险分层 TTL · 不搞一刀切
只读长有效期——查询类工具token 便利优先
常规中等有效期——点位读写按业务节奏授权
高危短有效期 + step-up——命令下发需重新换取授权，防止一张令牌长期横跳
TTL 阶梯按操作风险配置化（读多写少场景友好），细粒度在快速迭代中
一句话验收标准：能说清楚每一次智能体调用是谁授权的、能做什么、什么时候过期
