租户隔离的完整数据路径：多租户不是"查询时加个 where"

从请求进入到数据落库，租户上下文每一步都在场——工程纪律是"不提供任何绕过的捷径"
入口 请求进入Request In 网关解析令牌，确定调用者身份与所属租户——智能体调用同样在此定身份 tenant_id = ?
携带
API 层 租户上下文注入Context 请求上下文带租户信息进入业务层，后续所有读写默认继承 context.tenantId
传递
服务间 gRPC 携带租户Cross-Service 跨服务调用契约支持时必带租户 ID；跨服务取数先验证归属权再返回或变更 grpc: tenantId
落库
数据层 查询强制租户范围Persistence 业务表带租户字段，查询与写入均限定范围——上层数据中心、告警、AI 全部继承 WHERE tenant_id = ?
缓存层 · 最容易漏的一环
  • 租户数据的缓存键必须包含租户上下文
  • 否则跨租户读到脏缓存——隔离在缓存层穿帮
  • DC3 把它列为架构红线，而不是"最佳实践建议"
cache key = {tenant}:{entity}:{id}
为什么与 AI 直接相关
  • 智能体的工具调用运行在调用者的租户上下文里
  • A 饭店的智能体，根本查不到 B 饭店的设备——不在候选集，而非"查到再过滤"
  • 这正是 EP.06"不敢给"那道坎的底层答案
agent tool call → caller tenant scope
反模式红线
不提供 "tenantId IS NULL" 式的绕过捷径
除非数据模型显式定义为全局记录——图省事的"先查全量再内存过滤"是隔离穿帮的第一大来源，写在纪律里而不是靠 review 抓。
隔离检查清单：数据库 ✓ 缓存键 ✓ API 上下文 ✓ 服务间 gRPC ✓ —— 五处一致才算"全链路"
