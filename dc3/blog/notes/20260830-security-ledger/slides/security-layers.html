四层纵深防御：写进架构，而不是写进文档

智能体治理要求"可追溯"——通俗含义是：说清楚每次调用是谁授权的、做了什么、怎么追责
01TRANSPORT
传输层TLS / SSL
网关对外 TLS数据在路上不被窃听
内部连接按部署加密总线与存储连接可配
底线，不是亮点
02IDENTITY
身份层JWT + RBAC
一套身份三个入口Web / CLI / 智能体同一 OAuth 签发
RBAC 角色权限MCP scope 由 RBAC 投影
风险分层 TTL高危短令牌 + step-up
不给智能体特权模型
03TENANCY
租户层Isolation
数据库查询强制带租户范围
缓存键必含租户上下文
API / gRPC请求进入即解析租户 · 服务间携带
不提供绕过租户的捷径
04AUDIT
审计层Traceability
命令下发全量留痕谁 · 何时 · 对哪个设备 · 做了什么
事件与操作日志系统事件同样入账
智能体调用入审计令牌 + 授权来源可回溯
账本能翻到具体一次调用
一次智能体调用 · 逐层穿行
1
进入 TLS 通道
智能体客户端携带令牌请求 /mcp
2
网关验签 + scope 检查
RS256 验签 · 确认"只读"能力边界
3
租户上下文贯穿查询
跨租户设备不在候选集
4
调用与结果入审计
具体令牌、授权来源可回溯
任何一层不满足，调用终止 · 高危动作另需人确认执行
诚实口径：纵深防御 = 提高攻击成本 + 保留追责证据，不是承诺零风险 漏洞响应见仓库 SECURITY.md
