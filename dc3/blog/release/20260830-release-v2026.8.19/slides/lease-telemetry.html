租约围栏的持久化遥测：不丢、不重是怎么做出来的

提交 956de3dd3（breaking change）· 驱动遥测链路的分布式正确性改造
BREAKING：驱动需强制配置 durable outbox租约感知的所有权与遥测契约
四段机制 · 怎么做的
PG 租约 + Fencing
PostgreSQL 租约声明分布式所有权；fencing 令牌保证失效实例旧请求失效——多驱动实例 / 故障切换不会双写
先落盘
SQLite Durable Outbox
遥测必须先进持久化外发箱才允许发布到 RabbitMQ——发布前的状态是可恢复的，不是易失的
再发布
RabbitMQ 发布
消息带围栏契约进入总线，重发场景与所有权变更场景被契约约束
幂等消费
数据中心摄取
摄取事务化 + 幂等：重复投递落库结果一致，失败回滚不产生半批
为什么这样做
重发与去重是一对：R2 的缓冲重发保证"不丢"，但重发必然带来重复——本版本在摄取侧用幂等把"不重"补齐，链路语义闭环为 at-least-once + 幂等 = 效果恰好一次
所有权问题必须显式解：两个驱动实例同时认为"我负责这批设备"时，谁说了算？租约 + fencing 是分布式系统的标准答案，而不是靠"部署时别这么干"
outbox 是发布的前置条件：先持久化再发布，崩溃恢复后从外发箱续传——发布行为从"尽力而为"变成"可续传的事务"
升级注意（breaking）
驱动侧必须配置 durable outbox——这是硬性要求，不是可选项；升级前先确认驱动部署带持久化卷
遥测契约变更：驱动与数据中心需成对升级，跨版本混布不在兼容承诺内
为什么敢于 breaking：遥测正确性是采集平台的根，根上的账越早算清越好——发布说明与迁移要点见仓库 changelog
一句话：缓冲（R2）管丢不丢，租约围栏（本版）管重不重——采集正确性两条腿终于都齐了
