IoT DC3 · Release R4 v2026.7.3 · 特性详解 2/2

租户硬隔离：MyBatis-Plus 拦截器 + fail-closed + 白名单豁免

隔离不靠每个查询自觉带 where——拦截器在 SQL 层统一兜底，默认拒绝、显式豁免
① 请求进入 解析租户上下文 网关 / 服务入口解析调用者租户身份；智能体调用同样在此定身份
SQL 改写
② 拦截器层 TenantLineInnerInterceptor 注册 TenantLineHandlerImpl：fail-closed——租户条件缺失默认拒绝，只有白名单内的表/路径放行；业务 BO 实现 TenantOwned 契约声明归属
越界即断
③ 异常面 TenantNotScopedException 越权访问抛出专用异常，映射为 500 而非静默空结果——错误要响，数据不能错
runIgnore：显式豁免机制
不是所有路径都该带租户条件——登录前 token、公共元数据属于请求期无租户路径
豁免用 runIgnore 显式声明并集中 review，而不是散落的"忘了拼 where"
本版本豁免三类：网关 MCP 公共端点、OAuth 公共端点、request-time 无租户路径
权限查找路径同步 bypass 拦截器（权限表本身是全局资源）
豁免是显式白名单的一部分，与 fail-closed 共同构成"默认安全"
服务间也要隔离
gRPC 服务端绑定租户上下文：跨服务调用到达时恢复租户身份，DriverRegisterServiceImpl 等 gRPC 路径逐一接入
移除各 Manager 模块里冗余的手写租户过滤——拦截器已统一兜底，重复过滤反而掩盖漏配
为什么这样做：隔离逻辑只活在一处（拦截器），业务代码零心智负担；白名单是唯一逃生门，且必须过 review
一条工程纪律
多租户最大的风险不是"没有隔离"，是看起来有隔离——某条查询忘了带 where，测试环境发现不了
fail-closed 的含义：缺省即拒绝。新增表/路径必须显式决定"带租户"还是"进白名单"，没有第三种沉默状态
这正与同期网关 MCP 公共端点的 runIgnore 豁免设计闭环——先堵后疏
验收口径：业务代码不再手写租户 where · 越权抛异常而非静默 · 豁免集中白名单 · gRPC 全路径恢复上下文
