IoT DC3 · Release R3 v2026.6.26 · 特性详解 1/2

AI 中心迁移 Spring AI 2.0：做了什么，怎么做的，为什么

dc3-center-agentic 是平台的 AI 编排中枢 · 本次升级让它站在 Spring 官方 AI 栈的最新稳定线上
怎么做的 · 三步迁移
① 工具 API 迁移 spring-ai 2.0.0
Tool Calling 接口从旧版注解模型切到 Spring AI 2 的工具定义——平台把"查设备、读写点位"注册为标准工具的代码路径整体重写，模型侧调用方式不变。
② JSON Schema 生成对齐 victools jsonschema 5.0.0
工具参数的 JSON Schema 由 victools 生成，版本对齐到 5.0.0 消除生成结果与 Spring AI 2 校验器的字段类型漂移，并同步更新工具 API 测试用例。
③ 依赖治理 okhttp
补齐模型 HTTP 客户端依赖声明，避免隐式传递依赖在升级后运行期才爆——依赖显式化是这次迁移的纪律。
升级后的能力面
Tool Calling 受控调用：模型经工具查设备、读写点位，全部落在调用者权限与租户上下文内
模型提供者管理（model provider service）：多模型接入与配置化管理
动作服务（action service）：AI 产出的动作建议走统一执行通道
会话记忆持久化：多轮上下文入库，跨端登录不丢
告警根因辅助分析：产出建议供运维决策，处置仍走命令链路
为什么这样做
站在官方主线上。Spring AI 2 是 Spring 官方 AI 栈的当前主线，早迁移早收敛：工具 API 的破坏性调整越晚做，改的面积越大。
为工具面扩展铺路。统一的工具定义与 Schema 生成，是后续把更多平台能力（存储分析、告警深挖）开放给模型的基础设施。
测试先行。工具 API 测试用例随迁移同步更新——迁移的验收标准不是"能编译"，是行为一致。
升级口径：模型可插拔不变（GPT / Claude / DeepSeek / Qwen），变的是工具调用底座——这正是平台层该守住的边界
